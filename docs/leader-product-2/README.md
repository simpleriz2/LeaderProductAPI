## ADR-008: explicit unreleased module compatibility format
Accepted: manifest **format2** replaces the local, never deployed format1 prototype; old formats fail closed. Each artifact must declare `requires.minHost`, exact native capability revisions and exact semantic port versions. Host context supplies explicit supported revision/version sets plus supported exported module contracts. Higher revision alone never implies backwards compatibility. Shared runtime family remains an independent compatibility gate; source fingerprint identifies the actual APK/bundle pair. Signed metadata cannot make unavailable native code appear. Empty requirements on QR/Help probes describe delivery fixtures only, not working camera/chat features.
No deployed/offline client exists on these prototype formats. Future deployed format evolution must retain an explicit offline compatibility window/migration path; rejecting local format1 is not a production update strategy. Business API compatibility and key rotation remain separate backlog items.

## ADR: API compatibility window for previously assigned clients
Local Central retains exact company/platform assignment history. A Company-scoped token may explicitly request activeReleaseId from that history; it carries the immutable release's API contract. A newer assignment does not silently upgrade the old client's API contract. Artifact tokens still pin the assigned candidate, independent of the caller's active code. Unknown/cross-company/cross-platform releases are denied.
Company API rollout declares an explicit bounded exact-version support window. Assignment fails before registration if that API contract is not deployed. During old/new overlap both clients work; retirement rejects old token issuance and already-issued token requests (409/update required) after mandatory live Central introspection. Revocation still yields unauthorized. No positive authorization cache/local-JWT fallback added.
This is an in-memory local protocol pilot, not persistent release history, distributed deployment orchestration, real schema compatibility, or product completion. Existing probes omit activeReleaseId for compatibility and use their current assignment; every future business composition must pass its verified ACTIVE release explicitly, handle update-required without deleting drafts, and route versioned Company handlers. Retiring support for offline clients is an explicit rollout decision, not automatic on assignment. Persistent audit/provenance, API handlers for actual business domains and staged deployment remain backlog.

Schema versions1 identity/QR are checked; migration is additive/idempotent and rejects unknown retained versions, serialized by transaction advisory lock. No legacy table import/deletion.

## QR server migration1->2: immutable create receipts
New 002_create_receipts.sql preserves migration1 and upgrades QR server schema to2; client QR draft schema remains1 (separate owners/databases). Repository requires the installed exact server schema. Create requires a UUID operationId; canonical bounded content SHA256, company/local-owner/operation identity, transaction advisory lock and receipt+document in one PG transaction prevent duplicate creation under concurrent retries. Identical retries return the immutable original response even after later edits; a changed payload conflicts409. Object read after acknowledgement fetches current state. No cross-user/company receipt lookup or cache-based authorization. Retention/reconciliation policy and HTTP/client outbox adoption remain pending; receipts are not deleted automatically.
