# Legacy realtime subscription hardening — 2026-11-17

Current dev unrestricted generic join was replaced by registerAuthorizedSubscriptions. Only user:<self>, permitted department:<id>, and object-authorized appeal:<id> are accepted. Help rooms remain accessible only through existing protected Help protocol; raw presence rooms cannot bypass its dedicated handler. User identity/role/status are loaded from DB; JWT role claims are not used as subscription grants. Appeal visibility matches GET /appeals/:id (creator/assignee/target department member or manager/admin) plus view_appeal and current service entitlement. No positive grant cache across joins.

Presence subscriptions and GET /users/presence share one policy: current active targets and self, administrative user-management rights, common employee department, visible Help participants/message authors (existing Help actor/service rules), or visible Appeal creator/assignees (same object/service rules). Unauthorized IDs are filtered. This narrows the former unrestricted presence endpoint; source scenarios using profile/Help/appeal participants require native/Web parity checks. No production tests or deployment occurred.

Subscription processing: at most 4 concurrent authorizations / 128 queued+active operations; at most 128 rooms/socket and 100 presence IDs/request. Payload/room validation happens before queuing. Closed/expired socket cannot join after a delayed query. Denial/DB errors return safe optional acknowledgements, without stale cached success. Queuing preserves normal reconnect bursts across multiple departments.

Evidence: TypeScript passes; 16 new unit tests; combined 10-suite regression (security + existing submission/idempotency/receipt/worker/tracking/refresh/push) 116 tests passed. Security + existing Help socket tests: 24 tests passed. Actual loopback Socket.IO/WebSocket integration test passed, proving room refusal and authorized presence joins on the wire with injected fixture identity/policy. It does NOT validate real PostgreSQL grants or production JWT/Central auth.

Limits/backlog: legacy Prisma schema has no SaaS company tenancy; these policies protect existing single Company DB objects, not cross-company SaaS isolation. Central introspection remains required in the replacement Company API (pilot tests it). Current joins are authorization snapshots: already-open rooms need revocation/ACL-change revalidation and data-safe invalidation events; outbound delivery authorization and cluster presence/drain remain pending. JWT secret defaults remain legacy debt and must be removed before any exposed fork runtime. Do not expose the legacy server or describe this as completed Stage 3 security acceptance.
